# REQ-0020:D34密钥轮换第一步双钥过渡

## Scenario

签发私钥原值不可达（旧仓 GitHub Secret 不可读加本机无副本），按 D34 既有轮换协议（catalog.rs 公钥块注释：先发版同时内嵌新旧两把公钥，任一验过即通过，再换私钥重签云端件，机器更新完后摘掉旧钥）启动密钥轮换：新钥已在本机生成落位（key id EB15358F893ED0DB，`~/.config/ome/catalog-signing.key`）。本件为第一步独立小件：只动验证面信任锚（二进制内嵌公钥扩双钥），云端清单重签归签发侧后续批次。

## Criteria

- [x] `CLOUD_CATALOG_PUBKEYS` 扩双元素：旧钥 FB93BFD3788C2316 居首不变，新钥 EB15358F893ED0DB 追加第二；`verify_with_embedded_keys` 既有「任一验过即通过」语义直接生效（验证逻辑零改动，D34 轮换当初的预设面）
- [x] key id 单值数组化：`CLOUD_CATALOG_PUBKEY_ID` 更名 `CLOUD_CATALOG_PUBKEY_IDS`（与公钥数组同序）；两处展示面（签名校验失败提示、`catalog status` 的 `pubkey` 字段）并列双 id（`/` 连接）
- [x] 注释按既有轮换协议口径补双钥过渡期句（全端铺开新 ark 后摘旧钥收单）
- [x] 新钥公钥进仓库：`.tools/catalog-sign/catalog-signing-new.pub` 过渡期文件（摘旧钥收尾时转正位文件）；`内嵌公钥与仓库公钥文件一致` 单测扩双文件机检
- [x] 测试：双钥三态单测（同内容旧钥签名过、新钥签名过、一次性废钥合法签名拒）加独立源交叉验证（catalog-sign verify：新钥签×新 pub 过、新钥签×旧 pub 拒、错钥×双 pub 拒，证双钥向量非同钥双签）
- [x] 门禁：cargo fmt 加 clippy（`--release --locked --all-targets`）加 `cargo test --release --locked` 全绿（246 项，新增一件）；rumdl 加 md 三扫描加 llms-guard 加 project-evo check 绿；aidoc 投影再生成加 `--check --strict` 过

## 边界与分工

- 云端清单重签（tools.toml 与 manifest.toml 的 `.minisig` 换新钥签）归签发侧（ohmycloud）后续批次：本件只动验证面，不动签发面；双钥版铺开前后新旧签名件都验得过，无缝过渡。
- 摘旧钥收尾（PUBKEYS 收单、`CLOUD_CATALOG_PUBKEY_IDS` 收单、SELFTEST_SIG 撤换正位、catalog-signing-new.pub 转正位）待全端铺开双钥版 ark 后另批：届时既有测试按「预期红灯」口径引导同步。
- CI 密钥库（GitHub Secret `CATALOG_SIGNING_KEY`）换装新私钥归签发侧配置，不在本仓改动面。

## trace 回填区

- 向量生成（2026-10-11，catalog-sign 签署）：新钥私钥对新自检内容签出 `SELFTEST_SIG_ROTATED`；一次性废钥（key id 4A95257282439B25，私钥签署后 shred 销毁、公钥未内嵌未落库）同内容签出错钥向量 `SELFTEST_SIG_WRONGKEY`。
- 独立源交叉验证（catalog-sign verify，与引擎 minisign_verify 不同实现路径）：新钥签×新 pub `verify=ok`；新钥签×旧 pub 拒（key id EB15358F893ED0DB ≠ FB93BFD3788C2316）；错钥×新 pub 拒；错钥×旧 pub 拒。
- 测试：`cargo test --release --locked` 全绿 246 项（新增 `验签_双钥过渡期旧钥新钥任一过且错钥拒`，扩 `内嵌公钥与仓库公钥文件一致`）；`cargo fmt --check` 与 `cargo clippy --release --locked --all-targets` exit 0（存量告警在未动文件）；`cargo aidoc --check --strict` 过（`CLOUD_CATALOG_PUBKEY_IDS` 投影同步）。
- 实质代码改动门核对：本件为常量面加注释加测试向量（无新模块、无跨文件接线、无并发与进程管理），不触对线强制类；信任锚属安全敏面，以独立源交叉验证四态补证。
