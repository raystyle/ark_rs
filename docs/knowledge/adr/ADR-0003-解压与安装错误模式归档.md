| M017 | 2026-09-11 | 已修正（2026-09-11） | `post_install` 受控命令在 300s 窗口内不退出被判超时杀进程（误报）；本机实证：`cmd /c` 循环输出约 1.2MB 时父进程 `try_wait` 轮询 10s 仍 `None`，加抽干线程后同一命令 0.76s 正常退出 | 子进程 stdout/stderr 建了管道但父进程只在**失败后**才读：输出超过管道缓冲（约 64KB）时子进程写端阻塞不退出，父进程判定树里既没读也没超时感知，只剩超时一路退出（`kill` 后误报超时而非报真实结果） | 管道面铁律：**凡接管道必并发抽干**（读线程或异步读），不要「等退出再读」；尾窗滚动保留最近 64KiB 即可（既抽干又不随输出吃内存），回传等待设上限（后台孙进程持写端不关时不无限等）；杀进程后补 `wait` 回收。回归测试用「输出远超缓冲的正常命令 + 小超时窗口」构造（旧码必超时，新码亚秒过） |
| M021 | 2026-09-11 | 已修正（2026-09-11） | Windows 超时终止 `post_install` 后 `cmd /c` 的孙进程（ping 等）仍存活；补的 `taskkill /PID x /T /F` 打印 `ERROR: The process "x" not found.` 完全无效 | 补杀顺序错：先 `child.kill()` 加 `wait()` 再 taskkill，父进程已死，而 `taskkill /T` 靠「父进程在位」沿进程树找子进程（本机 A/B 实证：kill 先则 taskkill 失效且孙进程存活，taskkill 先则整棵清掉 SUCCESS 三连） | 顺序红线：**父进程还活着时先 `taskkill /PID x /T /F`，再 `kill` 加 `wait` 兜底与回收**；断言要能证伪：用例在超时后跑 `tasklist /FI "IMAGENAME eq ping.exe" /NH` 断无残留，且比对必须大小写不敏感（tasklist 输出 `PING.EXE`，首版小写断言在旧顺序下也过，属假绿） |
| M022 | 2026-09-11 | 已修正（2026-09-11） | 共识② 上提后，uv-git 与 npm-tgz 通道的 env_set 仍被跳过（首次装不配用户级变量，重装才补），且同一段原语逻辑存在三份实现（主链幂等分支、主链成功尾、新 helper），shims 失败语义已分叉（主链硬错、helper 降 WARN） | 逐通道复制「应用 manifest 原语」的代码块，而不是抽一个全链应用点：复制到第三份时漏掉 env_set 一项（只搬了 shims 与 post_install），且复制时顺手改了失败语义；`clippy` 的 too_many_arguments 8/7 警告同源（为传 manifest 给通道函数加参） | 原语应用点收成**唯一实现** `apply_manifest_primitives`（L1 env_set 与 shims 硬错、L2 post_install 降 WARN），主链两处与两早退通道共用；通道调用点放在调用侧而非穿参（签名不膨胀）；教训：新面接线先找既有同类应用点，能抽一个就不复制第二份（双份并行必漂移），`clippy` 警告要跑在「提交前最后一次改动之后」 |
| M023 | 2026-09-11 | 已修正（2026-09-11） | POSIX 用户 bin 直链只在「悬空」时重建，**有效但指向旧 target 的链接会永久留着**：版本目录型布局（如 zig 的 `~/zig/zig-x86_64-linux-0.16.0`）升级换目录后，`~/.local/bin/zig` 仍指旧版，PATH 顺序在前即陈旧遮蔽 | 幂等判据用了 `dst.exists()`（跟随链接，指向存在的旧文件就算「完好」）而没有比对 `read_link` 的实际 target；旧版本目录升级后通常不删，故悬空分支永不触发 | 幂等判据要**比对语义而非存在性**：`read_link(dst) == exe` 才跳过；指向别处（含悬空）先删再建；落点是真文件（用户自装）不动；exe 本就落该目录时不建自指链接。落点语义抽成可测函数并补六态用例（首验于 WSL）。同轮：一次性行内改写脚本 `.tools/tmp_fix.py` 不该进仓（命名、PEP 723 头、清单登记三规皆违） |
