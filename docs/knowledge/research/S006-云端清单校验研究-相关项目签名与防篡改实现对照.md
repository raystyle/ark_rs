# S006-云端清单校验研究-相关项目签名与防篡改实现对照

> 主题：为「云端软件清单防 MITM 的非对称校验」做实现对照：相关项目把信任根放在哪、怎么签、怎么验、能防哪类攻击、代价多大。2026-09-10 用户指令「研究一下相关项目如何实现」（前一轮方向：本地和云端一起非对称校验，像 SOPS 的方式）。

## 一、结论速览

| 项目 | 校验对象 | 算法与载体 | 信任根与获取方式 | 主要防住 |
| --- | --- | --- | --- | --- |
| SOPS | 配置文件 | 无签名；CMS 加密加文件内 MAC | 接收方私钥（age/PGP/KMS）解密 | 检测文件被改动；不证明作者 |
| minisign 与 signify | 任意文件 | Ed25519，分离的 `.minisig` 文件 | 公钥由发布渠道公布，校验方手动指定 | 伪造与篡改 |
| Sparkle | 应用更新包与 appcast | Ed25519，公钥内嵌应用 | `SUPublicEDKey` 编译进应用 | 伪造更新、投毒 feed |
| apt 与 Debian | 仓库元数据（Release 与 InRelease） | OpenPGP 签名 | 发行版 keyring 预装在系统 | 仓库被镜像方或中间人改写 |
| RPM 与 Fedora | 仓库元数据（repomd.xml.asc） | OpenPGP 签名 | 发行版 keys 包预装 | 同上 |
| PyPI | 索引与包元数据 | TUF 多角色签名（PEP 458） | 离线根密钥，客户端预置根元数据 | 篡改、回滚、冻结 |
| npm | 包版本元数据 | ECDSA 签名（`dist.signatures` 加 keyid） | 公钥从 registry 的 `/-/npm/v1/keys` 取 | 元数据被第三方篡改 |
| Helm | chart 包 | OpenPGP，`.prov` 随包分发 | 用户持有的 keyring 与 key 名 | chart 被替换 |
| Kubernetes | 发布二进制与镜像 | Sigstore 无钥签名（cosign） | 证书身份与发行者（OIDC）断言 | 伪造发布物 |
| GitHub Artifact Attestations | 构建产物 | Sigstore 证明 | `gh attestation verify` 绑定仓库身份 | 产物与仓库构建脱钩 |
| HashiCorp（Terraform 等） | 二进制与 SHA256SUMS | OpenPGP 签名（`.sig`） | 官方公布的公钥 | 校验清单被替换 |
| Rust 工具链 | channel 清单 | 只有 `.sha256` 边车 | HTTPS 与域名 | 传输损坏；不防同源替换 |
| winget 与 Scoop | 安装包 | 清单内 `InstallerSha256` | 清单仓库与 GitHub 的信任 | 下载物与清单不符 |

## 二、SOPS 的真实模型

- SOPS 是加密编辑器：用 age、PGP、KMS 等身份对数据密钥做封装，文件内保留加密后的数据与元数据。[实证: getsops 文档站与仓内 README 抓取 2026-09-10]
- 它提供 MAC 用于发现文件被改动，但 MAC 密钥与数据在同一个文件里（随接收方公钥加密），因此能防「无钥者改动」，不构成「作者真实性」；谁持钥谁都能重算。[推断: 由其加密模型与 MAC 密钥存放方式推出]
- age 本身不提供签名能力（README 未见签名面，只有加密与身份）。[实证: age README 抓取]
- 结论：用户说的「像 SOPS 的方式」可直接吸收的是密钥分工与保管（公钥标识进配置、私钥只在本地与 CI 密钥库、支持多接收方与轮换），校验载体应取**签名**（Ed25519 系）而不是加密。

## 三、四种实现模式

1. **分离签名加预置信任根**：apt、RPM、Helm、HashiCorp、minisign 都属于此类。签名与产物并列分发，客户端预装或手动指定公钥。apt 另设 `Valid-Until` 防冻结，签名只覆盖仓库元数据而不逐个包校验（`apt-secure` 明说包级校验要另用 debsig-verify）。[实证: apt-secure man 页抓取]
2. **公钥内嵌二进制加随件签名**：Sparkle 最典型。发布方用 `generate_keys` 生成 Ed25519 密钥对，公钥以 base64 写入应用 `Info.plist` 的 `SUPublicEDKey`，更新包与 appcast 均签名，并给出密钥轮换规则（换钥需一次更新同时改代码签名或走 dmg 限制路径）。[实证: Sparkle 文档抓取]
3. **元数据分层加过期与版本**：TUF 与 PyPI PEP 458。用 root、timestamp、snapshot、targets 多角色与离线根密钥，显式对抗回滚攻击（提供比客户端已见更旧的元数据）与冻结攻击（不再提供更新）。[实证: TUF 规范与 PEP 458 抓取]
4. **同源提供密钥**：npm 的做法，`dist.signatures` 里带 keyid 与签名，公钥从 registry 的 `/-/npm/v1/keys` 获取；npm 文档给的签名对象是 `包名@版本:integrity`。GitHub Artifact Attestations 类似，靠 OIDC 身份与仓库绑定。[实证: npm 文档与 keys 端点、GitHub 文档抓取]

## 四、攻击面对照

| 攻击 | 只有 sha 边车（现状） | 分离签名加内嵌公钥 | 再加客户端序号（防回滚） | TUF 全量 |
| --- | --- | --- | --- | --- |
| 传输被改（TLS 之外的中转改写） | 可发现（边车与清单同请求链时） | 挡住 | 挡住 | 挡住 |
| 镜像桶或 CDN 凭据泄露被写入 | 挡不住（可同时替换边车） | 挡住 | 挡住 | 挡住 |
| 客户端本地副本被改 | 挡不住 | 挡住 | 挡住 | 挡住 |
| 回滚到旧但真实的清单 | 挡不住 | 挡不住 | 挡住 | 挡住 |
| 私钥或 CI 密钥泄露 | 不适用 | 失效，需换钥发版 | 失效，需换钥发版 | 失效，root 密钥离线可救 |

## 五、对 ome 的候选与建议

- **候选 A（建议第一步）**：Ed25519 分离签名（minisign 格式），公钥内嵌 ome 二进制，云端同时分发 `ome/catalog/tools.toml.minisig`；刷新落位时连同签名一起落位到部署副本目录，命令加载清单前校验。这样「本地与云端一起校验」用同一把非对称密钥实现：云端拉取防 MITM，本地副本防篡改。
- **候选 B（加固，建议第二步）**：清单内加 `generated_at` 与单调 `seq`，客户端把已见 `seq` 记在 `.last-sync`，拒绝更旧版本，补上回滚防护（TUF 的简化版）。
- **候选 C（按需）**：完整 TUF 或 Sigstore 无钥签名；复杂度与依赖显著上升，收益主要是密钥轮换与回滚，短期不划算。
- **密钥管理**：私钥存 GitHub Secret（CI 签云端件）与本机 `~/.config/ome/`（本地开发签或应急重签，与 sops 私钥同域习惯）；公钥随二进制发版，轮换时先内嵌新旧双公钥过渡一轮再切换；撤销走换钥加发版加重签云端件。
- **与现状衔接**：sha 边车继续保留（缓存击穿与传输完整性的廉价检查），签名作为信任根判定；仓库开发面不参与签名以避免开发流程卡顿，部署副本与云端件强校验。
- **待用户裁**：签名密钥由 ome 仓 CI 持有还是沿用已有 age 或 SSH 密钥体系；本地副本校验是默认阻断还是先告警一段时间再收紧。
